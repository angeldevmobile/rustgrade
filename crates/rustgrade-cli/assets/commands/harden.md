---
description: Make Rust code survive hostile input, proving each fix with a test that failed first
argument-hint: "[path or function]"
---

Harden the Rust code at `$ARGUMENTS` (the current crate if empty) against input
it does not control. Use the rustgrade skill and its `references/errors.md`.

Run shell commands **one at a time**, never chained or in parallel: cargo holds
file locks, and on Windows a concurrent build fails with `os error 32`.

A hazard only counts if a test shows it. Do not fix what you cannot demonstrate.

1. **Find the boundary.** List the entry points that receive data from outside:
   sockets, files, CLI arguments, environment, deserialization, public library
   functions. State what each one may assume. If nothing crosses a boundary, say
   so and stop.
2. **Baseline.** Run `cargo test`, then `rustgrade scan <path> --format json` if
   the CLI is installed, then:
   `cargo clippy --all-targets -- -A clippy::all -W clippy::unwrap_used -W clippy::expect_used -W clippy::panic -W clippy::indexing_slicing -W clippy::arithmetic_side_effects -W clippy::cast_possible_truncation`
   These are leads, not verdicts: most will be fine.
3. **Attack each path from the boundary inward.** For every value the outside
   controls, ask:
   - **Panics:** `unwrap`, `expect`, indexing, slicing, slicing a `str` off a char
     boundary, division by zero, `RefCell` borrows, `unreachable!`.
   - **Numbers:** a length or offset that overflows when added or multiplied
     (release builds wrap silently), an `as` cast that truncates, a parser that
     accepts what the format forbids (`from_str_radix` takes a leading `+`).
   - **Resources:** `Vec::with_capacity(len)` with a length from the input,
     buffers or collections with no limit, recursion whose depth the input
     chooses, work quadratic in the input size, a read or a loop with no timeout.
   - **Pieces:** input split at every byte, empty input, input ending mid-value,
     the maximum and the maximum plus one of each limit.
   - **State:** what the next call sees after an error, whether a failure leaves
     partial writes, whether an early return skips cleanup.
4. **For each real hazard, in order of damage:**
   1. Write the smallest test that shows it, and run it to see it fail. If it
      passes, the hazard is not real: drop it and don't change the code.
   2. Make the smallest fix: a typed error, a checked operation, a limit. Keep
      public signatures unless the bug is in the signature; if so, ask first. If
      the fix changes what callers can observe (a call that waited now returns an
      error), it is a decision for the user: note it for the report. If you leave
      a real hazard open for that decision, keep its test with
      `#[ignore = "why it is open"]` and report it as open.
   3. Run the test to see it pass.

   Keep the tests: they are the proof. Add a deterministic loop over
   generated bytes when the code parses input, unless the crate already has a
   fuzz target or property tests to extend.
5. **Verify.** After your last edit, run `cargo test`, the scan and the clippy
   command again, all three, even if you only touched tests. Nothing that passed
   may fail now. A remaining lead is either fixed or explained: an
   invariant comment, or a `// rustgrade: allow(rule-id) reason` when the scanner
   cannot see why the code is right.
6. **Report.** One line per fixed hazard, most damaging first:
   `**[high]** src/frame.rs:42 · length + 4 wraps on a 32-bit size → checked_add, test `oversized_length_is_rejected``
   Then, under **Contract changes**, each change callers can observe and why, or
   "none". Then what you checked and found sound, in one sentence, then what this did not
   cover (timing, concurrency, anything you could not test). Do not claim the code
   is secure: say what was tried.
